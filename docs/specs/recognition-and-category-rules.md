# 交易识别与自动分类升级规格

日期：2026-11-08。调研基线：f0a52a5，应用版本 0.5.91-v6。

状态：业务范围及测试边界已确认，已发布为 [Issue #5](https://github.com/karl1179090/huayoupu-ledger/issues/5)，标签为 `ready-for-agent`；尚未开始实现。

## Problem Statement

用户希望付款后自动得到可靠账单，但实际页面经常只有金额、简短商家名称或银行提醒，并不提供完整订单信息。当前流程已通过无障碍读取页面文字，却仍统一执行截图 OCR；它既没有利用可直接解析的节点，也不能可靠区分“页面没有该字段”和“节点没有暴露该字段”。

当前识别把整页近似当成一笔交易，遇到银行通知、服务通知与扣款卡混排、同屏新旧两笔交易时，会漏记、混用字段或把余额当成交易金额。银行凭证显示在微信内时，实际银行卡没有匹配成功还可能回退到微信钱包，导致余额错误。时间不足的凭证也需要一致、不中断记账的处理方式。

自动分类依赖少量固定关键词，难以表达同一平台的不同消费用途。用户无法在设置中完整维护自己的分类和匹配规则，旧分类名称又与部分内置输出不一致，影响选择、筛选和统计。

用户需要两项协同升级：更可靠地识别不完整和多笔交易凭证，并依据商家与订单内容为后续新账单应用可配置的分类规则。历史账单的类别、时间和钱包不应因这次升级或规则变化被重新推算。

## Solution

现场识别先读取当前页面的无障碍节点。对已经通过同页面节点与截图对照验证的版式，节点能产生有效交易候选时直接解析并保留截图；未知版式、关键解析失败或冲突时执行一次 OCR。导入图片直接使用 OCR。缺少商家、商品、订单号或时间并不单独要求追加 OCR，也不补猜页面没有的信息。

识别时先划分交易区块，再分别提取每笔交易的金额、商家、订单内容、银行或支付机构、付款账户和时间。缺少可用交易时间时使用本次识别时间，不为时间缺失增加确认步骤。银行钱包依据银行和卡尾等实际证据匹配；账户或收支方向不明确的候选仍需确认，确认前不改变钱包余额。

主动识别多笔页面时，每笔按完整本地日期与金额匹配历史账单，忽略时分秒。有历史匹配则跳过，没有匹配且满足其他入账条件的全部入账，包括较早发生但未入账的交易。用户可查看新增、跳过、待确认和失败的数量及明细，不必为正常候选逐笔勾选。

设置增加“分类管理”和“自动分类规则”入口。收入与支出分别维护单层分类；用户按商家、订单内容及可选来源设置条件，按列表顺序执行自定义规则，再使用启用的内置规则和“其他”兜底。人工分类始终保留，规则只影响后续新识别，不追溯旧账单。

首版银行提醒及多卡页支持摇一摇、快捷方式和图片导入；自动监控继续处理既有支持范围内的即时支付结果。所有识别与规则计算在本地完成。

## User Stories

以下按“作为某类用户，我希望获得某项能力，以便得到某种收益”的格式覆盖用户故事。

1. 作为付款后记账的用户，我希望已适配页面能直接利用无障碍节点，以便减少重复文字识别的等待。
2. 作为付款后记账的用户，我希望未知或解析异常的页面自动使用 OCR，以便仍能处理节点不足的凭证。
3. 作为导入截图的用户，我希望直接识别图片中的内容，以便不依赖原应用仍停留在交易页面。
4. 作为核对账单的用户，我希望节点识别后仍保存交易截图，以便日后追溯凭证。
5. 作为记账用户，我希望普通截图失败时仍可保存已可靠取得的节点结果并看到缺图提示，以便不因留档失败丢失交易。
6. 作为使用自动识别的用户，我希望应用继续遵守页面授权、窗口归属和敏感控件检查，以便采集始终限于允许处理的页面。
7. 作为记账用户，我希望缺少商品、订单号或完整商家名时保留已有信息，以便简略的支付成功页也能被处理。
8. 作为核对账单的用户，我希望原样看到页面给出的商家短名称，以便不会把推测的门店或商品当成原始信息。
9. 作为记账用户，我希望缺少交易时间时直接使用本次识别时间，以便不会仅因时间缺失被要求确认。
10. 作为补录历史截图的用户，我希望缺时间的旧截图也遵循相同回退规则，以便记账行为可预期。
11. 作为核对账单的用户，我希望知道时间来自凭证、年份推断还是识别时间回退，以便理解账单日期的依据。
12. 作为记账用户，我希望重试、排队恢复和跨日恢复继续使用原先固定的识别时间，以便同一任务不会改变账单日期。
13. 作为识别银行通知的用户，我希望识别只显示月日的交易日期，以便不会仅因缺少年份而忽略页面日期。
14. 作为查看历史消息的用户，我希望状态栏和消息时间不被当成交易时间，以便不会把浏览时刻误记成消费时刻。
15. 作为从微信识别银行提醒的用户，我希望付款账户按银行凭证匹配，以便交易记到实际银行卡。
16. 作为拥有多张银行卡的用户，我希望银行和卡尾共同匹配到唯一账户，以便不会选错卡。
17. 作为仅有一个同银行账户的用户，我希望没有卡尾时仍能匹配该账户，以便减少必要信息不足时的操作。
18. 作为核对银行交易的用户，我希望卡尾不符或账户有歧义时先确认，以便未确认前不会误扣微信或默认钱包。
19. 作为识别摘要通知的用户，我希望无法判断收支方向时先确认，以便“交易成功”不会一律被当成支出。
20. 作为识别扣款通知的用户，我希望区分实际扣款结果和付款偏好，以便钱包与真实发生的付款一致。
21. 作为识别混排通知的用户，我希望区分商家、服务商和发消息的银行，以便商家与分类依据正确。
22. 作为识别多个卡片的用户，我希望每张交易卡独立提取字段，以便不会把一笔的时间或卡尾拼到另一笔金额上。
23. 作为识别复杂页面的用户，我希望余额、积分、广告和服务开通通知被排除，以便不会产生虚假消费。
24. 作为识别多笔交易的用户，我希望按日期和金额检查历史，以便同日同额的已有账单被跳过。
25. 作为识别多笔交易的用户，我希望查历史时忽略小时和分钟，以便不同页面的时间精度不会影响既定规则。
26. 作为补记账单的用户，我希望未匹配历史的合格候选全部入账，以便较早但漏记的交易也能补齐。
27. 作为识别多笔交易的用户，我希望同批两张独立新卡不会互相充当历史记录，以便没有历史匹配时都能保存。
28. 作为记账用户，我希望看到每批新增、跳过、待确认和失败的结果，以便快速了解处理情况。
29. 作为记账用户，我希望批次中断后保留成功项并继续未完成项，以便重试不会重复记账或扣款。
30. 作为记账用户，我希望全部跳过的任务也有可恢复结果，以便重新打开应用后处理结论保持一致。
31. 作为手动触发识别的用户，我希望通过摇一摇、快捷方式或图片导入处理银行提醒和多卡页，以便按需补录交易。
32. 作为使用自动识别的用户，我希望普通聊天和银行消息列表不被持续自动扫描，以便识别范围符合本轮约定。
33. 作为维护账本的用户，我希望在设置里分别管理收入和支出分类，以便快速找到统一的分类入口。
34. 作为维护账本的用户，我希望添加、改名、排序和选择分类图标，以便分类适合自己的记账习惯。
35. 作为维护账本的用户，我希望记账、编辑、筛选、统计和规则目标共享分类目录，以便各入口显示一致。
36. 作为维护账本的用户，我希望删除已使用分类前看到影响并指定同方向替代分类，以便不会留下失效引用。
37. 作为维护账本的用户，我希望分类迁移失败时整体回滚，以便账单和规则不会只改了一半。
38. 作为维护账本的用户，我希望收入与支出各有不可删除的“其他”，以便没有匹配规则时始终有有效归属。
39. 作为升级应用的用户，我希望旧分类名称及已有归属被保留，以便升级不会自动合并或重分旧账单。
40. 作为导入账单的用户，我希望导入文件的明确类别被保留，以便导入不会重新套用自动分类规则。
41. 作为配置自动分类的用户，我希望按商家名称或订单内容设置规则，以便同一平台的不同消费能分到不同类别。
42. 作为配置自动分类的用户，我希望添加来源限制，以便相同关键词可以在不同来源下使用不同规则。
43. 作为配置自动分类的用户，我希望使用包含、等于、不包含和全部／任一满足，以便表达常见匹配需求。
44. 作为配置自动分类的用户，我希望缺字段时不命中文字条件，包括“不包含”，以便信息不足不会造成意外匹配。
45. 作为配置自动分类的用户，我希望比较时处理大小写、全半角和无意义空白，以便常见文字格式差异不会妨碍规则。
46. 作为配置自动分类的用户，我希望规则只匹配本笔交易的业务内容，以便广告、导航和手写记账备注不会误触发分类。
47. 作为配置自动分类的用户，我希望按列表顺序采用第一条命中的自定义规则，以便规则冲突可预测且可调整。
48. 作为配置自动分类的用户，我希望自定义规则优先于内置规则，以便自己的分类习惯得到执行。
49. 作为配置自动分类的用户，我希望单独启停内置规则或复制为自定义规则，以便调整系统默认行为。
50. 作为配置自动分类的用户，我希望在保存前测试输入或只读选择已有账单，以便看到命中条件、优先规则和最终分类。
51. 作为配置自动分类的用户，我希望无效条件和失效目标不能保存，以便规则运行时不会产生无效分类。
52. 作为编辑账单的用户，我希望能从当前账单预填一条规则并自行保存，以便方便复用分类经验。
53. 作为编辑账单的用户，我希望修改一次类别不会静默创建规则，以便一次性调整不会影响未来账单。
54. 作为已手动分类的用户，我希望补充凭证或重新识别同单时保留类别，以便人工决定不会被机器覆盖。
55. 作为修改规则的用户，我希望新配置只影响之后新建的识别任务，以便旧账单和排队任务的行为保持稳定。
56. 作为核对账单的用户，我希望看到简短的分类命中说明，以便理解自动选择的原因。
57. 作为删除分类的用户，我希望排队任务也使用有效替代分类，以便旧快照不会复活已经删除的分类。
58. 作为备份账本的用户，我希望分类、规则、必要快照和处理结果随备份保留，以便恢复后可以继续使用和解释账单。
59. 作为合并备份的用户，我希望冲突规则不会静默覆盖本地规则，以便自己的配置得到保留。
60. 作为使用本地记账的用户，我希望新能力继续离线完成，以便不增加远程识别服务依赖。

## Implementation Decisions

### 领域与模块边界

- 沿用账单、分类、分类规则、订单内容、交易凭证、交易候选、商家、服务商、来源应用、凭证来源、付款账户及各类时间的领域定义。来源应用不等于实际付款账户，凭证来源不等于商家。
- 纯解析、时间解析、分类匹配及历史匹配计算放在 core。Android 层负责采集与识别编排，存储层负责事务、资金效果和提交回执，WebView 与桥接层提供设置及结果展示。
- 扩展既有识别编排和 CaptureCoordinator 提交边界，使一个任务可以提交一个或多个有区块身份的交易候选，并返回逐项处理结果及批次摘要。单笔调用保持兼容。
- 节点与 OCR 统一进入交易区块及结构化候选模型。候选携带原始文字、必要位置／层级关联、字段来源、交易状态、金额、方向、商家、服务商、订单内容、账户证据和时间证据。缺值与推断结果不能伪装成凭证明示字段。
- 页面分区模块不修改余额，分类引擎只计算分类，不改变方向、退款／本人互转语义或钱包。不存在完整信息的页面不通过猜测补齐。

### 节点优先、OCR 和凭证留存

- 无障碍只读取对方应用公开的节点信息，例如文字、内容描述、层级、坐标、控件类型和状态；不提供后台订单查询能力。图片或自绘区域未公开文字时，不能从节点直接取得其中内容。
- 不能在 OCR 前通用地判定屏幕哪些文字没有被读取。节点数量、遍历完成或坐标覆盖率不能作为“页面信息完整”的证明。
- 采集保留可用于分区的必要层级和坐标。现场识别必须继续通过授权、白名单、当前窗口归属、密码／输入控件和遍历边界检查；节点快速路径不能绕过这些条件。
- 只有通过真实同页面节点快照与截图对照验证的版式才能启用节点直接解析。适配记录包含应用版本、系统、设备和已验证范围；缺少真实节点样本时继续走 OCR。
- 已验证版式产生有效候选时跳过 OCR；未知版式、关键解析失败或冲突时执行一次 OCR。图片导入直接 OCR。缺商家、商品、订单号或时间本身不强制触发 OCR。
- 截图与节点必须属于同一有效窗口和交易。截图仍用于留档；离开页面后使用已保存证据继续处理，不从新页面补旧交易字段。
- 普通截图失败或超时，在已有可靠且通过检查的节点结果时可保存并标明缺截图。隐私、系统保护、窗口身份或授权失败仍停止；不得通过补截其他页面绕过失败。
- 优先复用已缓存的可靠商家图标，无缓存时使用默认图标，不单为图标执行完整 OCR。后续正常 OCR 获得的可靠图标可以共享。
- 权限撤销和白名单变化继续保留既有取消语义；业务规则快照不等于采集授权。

### 交易分区与银行钱包

- 先按节点结构、重复卡头、局部版式及标签划分交易区块，再分别解析。不得把全页合成一笔，也不得跨卡拼接时间、金额或卡尾。
- 嵌套图片查看器需区分内层凭证、外层记录时间和页面推荐内容。纯服务通知、余额、积分、营销金额及导航不得生成消费候选。
- 商家短名称原样保存，缺商家显示未提供。明确商家、扣费服务商和银行消息作者分别保存；“优先从零钱支付”是偏好，“通过零钱扣款”是实际付款证据。
- 银行模板在同一卡片内组合银行、交易类型与尾号。保留人工锁定账户优先级；银行与卡尾唯一匹配时选卡，无尾号且本地唯一同银行账户时可匹配并记录依据。
- 有明确卡尾但匹配失败时，不降级为仅按银行匹配。多账户、无匹配或冲突时账户保持未定，进入待确认且不产生余额影响，不回退微信或默认账户。
- 已适配的“网上快捷支付”等交易类型可提供支出证据；泛化“交易成功提醒”不足以确定方向。方向不明进入待确认，账户余额及余额差不能单独证明方向或交易身份。
- 钱包修正覆盖解析、选择、正式入账门槛和余额生效。仅添加提示但仍让错误钱包扣款不满足规格。没有银行凭证证据的普通支付继续使用既有适用规则，不无条件扩张通用“付款方式”标签。

### 时间契约

- 有可用凭证明示交易时间或日期时优先采用；缺少可用时间时使用本次实际开始识别订单的时间，历史图片同样处理，不为时间缺失增加待确认步骤。
- 本次识别时间在首次处理时固定并持久化，同批缺时间候选共用；排队重试、跨日恢复及进程重启沿用该值。任务固定本地设备时区，不能在恢复时重新选取日期口径。
- 支持完整年月日、月日缺年、日期时间分行及仅日期。仅日期保留页面日期和精度；仅时分且无可确定日期时回退识别时间，并保留原文。
- 月日缺年以可信原始采集日期为参考，没有可信参考则使用识别日期，选择最近一个不晚于参考日期的合法日期，并标记年份推断。无效或无法解析的日期按缺时间回退。
- 状态栏、外层查看器、导入时刻和消息通知时间不直接冒充交易时间；不靠状态栏时分拼接交易日期。
- 保存原始时间文字、最终记账时间、精度和来源，界面可简短说明“使用识别时间”。本地日界使用日历日期，不能用固定 24 小时替代。旧账单时间不批量重算。

### 多笔历史匹配与恢复

- 日粒度历史匹配仅用于多候选页面，不全局替换单笔、退款、本人互转及 CSV 的既有专门规则。强交易身份和任务提交幂等独立保留。
- 业务匹配键为完整本地日期（年、月、日）与整数分金额，忽略时分秒。不自行追加商家、钱包或其他字段作为必要条件。缺时间使用已固定的识别日期。
- 历史基线包含本批开始前已正式入账且未删除的账单；待确认草稿不作为该粗粒度匹配的阻挡记录。已处理任务或强身份重复仍由独立幂等机制处理。
- 在账本事务内固定历史基线并保存逐项决定，然后开始候选提交。本批刚新增的候选不能成为本批后续候选的历史。
- 对基线中的日期与金额执行存在性判断。有匹配则跳过，无匹配且通过其他入账校验则全部入账，不只取最新一笔，不默认展示入账前逐笔选择。
- 同批两张独立同日同额新卡此前没有历史匹配时都可入账；若基线已有该日期与金额，两张都跳过，不按数量相减。不得用旧的弱时间窗口查重再次合并已确认独立的同批卡片。
- 父任务保存候选身份、结果和账单映射；每个候选使用独立且稳定的提交标识，不能把单笔操作键重复用于多次保存。
- 每笔账单、钱包影响和候选提交回执原子提交。批次可部分成功，中断后保留已成功项，只处理失败或未完成项，恢复不得重复扣款。
- 保存全部跳过的回执；恢复读取既有决定，不因历史后来新增、删除或变化而重新决策。任务状态写回失败时由账本回执恢复结果。
- 结果展示新增、跳过、待确认、失败数量及逐项原因。正常候选自动入账，账户或方向不明的候选仍按各自约束待确认。

### 分类目录、规则和设置

- 分类使用稳定标识，收入与支出分别维护单层目录，支持添加、删除、改名、排序和图标选择。各方向规范化名称唯一，跨方向同名分别存在；本人互转与手续费保留专门语义。
- 收入与支出各有受保护、不可删除的系统兜底“其他”。新预设使用统一界面短名称，解析器不能再自行创建同义分类名称。
- 设置增加分类管理及自动分类规则入口。手动记账、详情编辑、筛选、统计和规则目标共享目录；保存分类引用时校验存在及方向。
- 旧账单按原名和方向迁移到目录，不自动合并长短名称，不把陌生类别丢入“其他”。CSV 的“一级/二级”作为完整单层名称保留；手动或导入明确指定类别时沿用该类别。
- 无引用分类可以直接删除。存在账单、规则或排队快照引用时，先预览影响，要求同方向有效替代分类，禁止替代自身或删除受保护分类。
- 删除及引用迁移原子完成，失败回滚。为排队快照保留替代映射，不复活被删除类别，不改金额、记账时间、方向、钱包及余额。本期不新增分类删除的独立撤销机制。
- 每条分类规则包括名称、启停状态、方向、可选来源限制、条件、目标分类和顺序。条件支持包含、等于、不包含；整组条件支持全部或任一满足。
- 匹配输入限于商家，以及本笔交易区块内明确的商品说明、交易说明和订单备注。订单内容独立持久化并保留原文来源；用户手写记账备注、广告、优惠券、客服、积分、导航不自动混入。
- 来源限制依据实际包名或明确支付平台证据，图片导入和现场来源分开处理，不从任意全文猜测来源。
- 比较时统一全半角、大小写及无意义空白，保留原文；不做同音、模糊商家名或 OCR 数字猜测。缺字段对所有文字运算均返回不匹配，包括“不包含”。
- 优先级为人工指定分类、顺序第一条命中的自定义规则、启用的内置规则、相应方向“其他”。内置规则支持分别启停，通过复制为自定义规则调整条件；目标必须有效。
- 任务创建时固定完整规则配置，包括定义、顺序、状态、方向及目标；只记录可变规则 ID 不算快照。排队、重试、恢复使用该配置，删除目标时使用明确的替代映射。
- 保存分类来源、人工选择状态、规则版本和必要命中说明。已存在账单，包括同单后续补充识别，均不因新规则重分；旧日期的新导入凭证属于新识别任务，但若匹配已有交易仍保留其类别。
- 列表显示启停、条件摘要、目标和顺序；编辑器提供字段、运算、关键词、条件关系和来源限制。空条件、空关键词、无效目标或方向冲突不能保存。
- 规则测试支持手工输入或只读选择已有账单，展示命中条件、前置规则截获和最终类别，不改记录。账单编辑可预填“据此创建规则”，用户保存后才生效。
- 正常账单展示简短分类说明，配置版本等实现信息留在诊断。修改一次类别不会静默生成长期规则。

### 迁移、备份与交付顺序

- 数据扩展覆盖稳定分类标识、规则与不可变快照、订单内容、商家／服务商／凭证来源、字段与时间来源、分类来源和人工选择状态、多候选任务、提交映射及回执。
- 完整备份覆盖必要新状态；兼容旧备份及 CSV 文本类别，恢复不重新分类或重扣余额。合并时按方向、名称和稳定标识处理冲突，不静默覆盖本地规则；冲突导入规则停用并说明原因。
- 旧任务缺少新字段时使用升级时确定的基线配置，不读取之后创建的新规则。恢复同时遵守授权、时间与规则快照以及已提交回执。
- 数据库和备份版本在实现时按实际分支递增，不在规格中猜定版本号。继续使用本地识别与存储。
- 推荐顺序：合成样例和迁移基线；分类目录；规则引擎与设置；统一字段、时间和银行钱包；多笔提交与恢复；节点直接解析及 OCR 回退；完整回归与真机验证。各阶段均以外部行为验收，保留后续阶段需要的统一契约。

## Testing Decisions

- 用户已确认主要测试边界：从现有识别处理及提交入口驱动，观察账单、分类、钱包余额、提交回执与恢复结果。优先沿用 CaptureProcessor → CaptureCoordinator → 账本存储链路和真实测试数据库，只替换外部采集或 OCR 为合成输入，避免给内部辅助函数分别创建测试缝隙。
- 交易解析、分类规则和日期计算使用既有 core 公共入口的参数化行为用例覆盖组合边界；不重复断言私有实现步骤。采集及 OCR 选路、设置 UI 各保留必要边界测试，因为仅测试提交入口不能证明截图触发和用户操作正确。
- 一个好测试应从可复现输入说明结果，验证账单字段、记录数量、余额变化、规则选择、错误反馈或重启后的状态；事务失败测试验证所有关联结果一致。只在 OCR 选路及恢复复用属于明确行为时断言调用次数，不把所有内部调用顺序固定为契约。
- 所有凭证、卡号、商家和金额使用合成数据。不得提交用户提供的真实截图、真实交易文字或未脱敏诊断。模拟器合成页面不能作为真实支付应用兼容性的证明。

验收覆盖如下，金额与名称均由合成夹具提供：

| 编号 | 场景与输入 | 可观察的通过条件 |
| --- | --- | --- |
| T01 | 已验证版式、有效节点、截图成功 | 生成正确账单并留图，不调用 OCR；节点与图片来自同一有效窗口。 |
| T02 | 未知版式、关键解析失败或冲突；导入图片 | 使用 OCR，单次处理不会重复运行 OCR 补可选字段；导入不依赖原页面节点。 |
| T03 | 页面只有成功状态、简短商家与金额 | 保留短名称，不捏造商品或订单号；时间按回退规则处理，其他条件充分时入账。 |
| T04 | 普通截图失败；系统保护或窗口身份失败 | 前者可保存可靠节点结果并标明缺图；后者停止，不能采集其他页面或产生未经允许的新账单。 |
| T05 | 空树、敏感输入、密码、遍历截断、授权撤销 | 继续遵守既有采集拒绝及取消策略；队列恢复不重新授予权限。 |
| T06 | 图标有缓存、无缓存、正常 OCR 后获得图标 | 分别复用、默认、共享；不因缺图标额外运行 OCR。 |
| T07 | 查看器里的银行摘要与外围时间、推荐内容 | 只提取内层交易信息；外层时间不作为交易时间，方向或账户未知不扣余额。 |
| T08 | 服务开通通知与实际扣款卡混排 | 只产生真实交易候选；商家与服务商分开，实际零钱扣款优先于付款偏好。 |
| T09 | 两张银行卡片，均含金额、余额、卡尾 | 分别解析，无跨卡污染，余额不成为交易额；上下排列变化不影响对应字段。 |
| T10 | 银行与卡尾唯一匹配；无卡尾且同银行唯一账户 | 选择正确账户，正式入账后只对该账户产生一次正确影响。 |
| T11 | 卡尾不符、同银行多账户、无账户、证据冲突 | 保留待确认，不回退微信或默认账户，所有账户余额保持不变。 |
| T12 | 仅有“交易成功”；明确的已适配支出类型 | 前者不能仅凭该文案确定收支；后者按实际证据处理，商家缺失不单独阻止入账。 |
| T13 | 实时及历史截图均缺时间 | 使用首次固定识别时间，不因缺时间待确认；来源可见，原始字段仍为缺失。 |
| T14 | 完整日期、分行日期、仅日期、月日缺年、跨年、闰日、无效日期及仅时分 | 优先保留可用页面日期，按参考日推断年份并标记；不可用时稳定回退。 |
| T15 | 跨日重试、进程重启、时区变化及具有夏令时的日界 | 同任务识别时间与时区口径不变；按本地日历正确查询历史。 |
| T16 | 历史同日同额但时分不同、商家或钱包不同 | 多笔业务匹配仍跳过，不追加商家或钱包条件；不修改被匹配旧账单。 |
| T17 | 同额不同日；较早交易没有历史匹配 | 不因金额相同或交易较旧跳过，满足其他校验的候选全部入账。 |
| T18 | 同批两张独立同日同额新卡，历史无匹配／已有匹配 | 无匹配时分别入账；已有匹配时都跳过，非数量相减，结果不受本批写入顺序影响。 |
| T19 | 历史记录已删除或仍待确认；另有重复任务或强交易身份 | 前两者不阻挡日金额业务匹配；真正的任务／身份重复继续幂等处理。 |
| T20 | 批次全部跳过、部分成功、未完成项失败 | 数量及明细正确，成功项保留；重试只处理未完成项，不重复扣款。 |
| T21 | 候选回执提交失败；账本提交后任务写回失败 | 前者账单、余额及回执共同回滚；后者恢复已提交结果，不再次识别或扣款。 |
| T22 | 批次恢复前历史记录发生变化 | 使用已保存基线决定，不能改变已完成或全部跳过的处理结论。 |
| T23 | 同方向重名、跨方向同名、旧长短名称及“一级/二级”名称 | 校验同方向唯一，跨方向独立；迁移保留旧名和归属，不自动合并。 |
| T24 | 分类添加、改名、排序、图标及各页面查询 | 目录一致，手动记账、编辑、规则、筛选和统计同步反映变化。 |
| T25 | 删除有引用分类、选择非法替代、删除“其他”、迁移中途失败 | 先预览影响，合法替代才提交；不留下失效引用，失败整体回滚，资金字段不变。 |
| T26 | 包含／等于／不包含，全部／任一，缺字段及文字格式差异 | 符合条件语义；缺字段不命中负向条件；规范化不改原文或猜字。 |
| T27 | 自定义规则同时命中、停用、内置复制与停用、无规则命中 | 按优先级及列表首条决定，最终有有效同方向分类。 |
| T28 | 商家相同但订单用途不同，外围广告与手写记账备注含关键词 | 仅本交易结构化业务字段参与，外围文字不影响分类。 |
| T29 | 排队期间修改规则、目标分类被删除、任务中断或升级恢复 | 使用原配置快照及明确替代映射，不应用未来规则或复活旧目标。 |
| T30 | 旧账单、人工类别、同单补充、旧日期的新凭证、明确类别的 CSV | 不重分已有账单；新识别按任务快照，人工及导入明确类别保留。 |
| T31 | 规则测试与“据此创建规则” | 测试只读且解释最终命中；预填不保存，改一次类别不创建规则。 |
| T32 | 新旧数据库迁移、备份往返、重复合并、配置冲突及恢复失败 | 类别与必要状态保留；冲突规则不覆盖本地，失败不半恢复、不重扣余额。 |
| T33 | 单笔识别、退款、本人互转、手续费、CSV 原有场景 | 既有专门资金和身份规则通过回归，多笔日金额策略不扩散。 |
| T34 | 设置入口及规则编辑完整操作 | 可以管理分类和规则，非法输入有明确反馈，正常账单说明简短可理解。 |

沿用的测试先例：

- RecognitionCommitRecoveryTest 已通过真实识别处理链路和两个测试数据库验证提交后任务写回失败、回执失败回滚与恢复不重扣；作为多候选恢复的主要先例。
- CaptureSupplementTest 验证同单补充、原类别及用户编辑保留；WalletAcceptanceTest 验证账户选择、人工锁定、资金事务和重复提交。
- LedgerCsvImportTest 提供独立相同明细保留、稳定身份、批量写入及失败回滚的先例；复用测试思路，不照搬 CSV 的业务去重口径。
- NativeV2DataTest、WalletBackupTest 及 PortableImportAcceptanceTest 提供目录、迁移、备份和兼容行为的先例。
- PaymentPageDetectorTest、LocalOcrBillParserTest、PaymentMethodParserTest、WalletResolverTest 和 DuplicateDetectorTest 提供核心入口的行为测试模式。对本规格有意改变的银行回退行为，应更新旧断言，而不是保留错误预期。
- WechatAutoPaymentTest、PaymentVisitsTest、PaymentRecognitionQueueTest 和 PaymentWindowReadyTest 覆盖采集时序、窗口与队列边界；PaymentSettingsUiTest 及现有 WebView／浏览器回归提供设置页面验收方式。

实现完成后按 CONTRIBUTING 的受影响范围运行源码检查、核心与应用测试、Lint、浏览器回归及隔离模拟器集成检查。真实设备另记录节点、截图、OCR、解析和保存耗时、OCR 跳过比例及实际适配范围；不得以模拟器合成用例声称所有微信、银行或设备版本已兼容。本文编写阶段未执行这些功能测试。

## Out of Scope

- 自动重分类、批量修正旧账单时间或钱包，以及历史重分类入口。用户主动编辑、分类改名或删除替代属于明确管理操作，不受此排除项限制。
- 缺时间专用待确认流程；正常多笔候选默认逐项勾选或只入账最新一条。
- 多级分类、正则表达式、任意条件嵌套、整页原文默认匹配、模糊商家推断和 OCR 数字纠错猜测。
- 自动学习永久规则、修改一次类别即静默建规则，以及单独的分类删除撤销功能。
- 被动扫描普通聊天或银行通知列表、新增银行应用自动监控、自动导航其他页面寻找缺失订单信息。
- 读取后台订单、从截图恢复无障碍节点，或在未 OCR 前保证知道所有漏读字段。
- 把日金额匹配扩展成所有导入／退款／转账的统一查重算法，或自行加入商家／钱包条件改变用户指定口径。
- 远程 AI、云端识别或新远程服务依赖，以及未验证的全设备兼容性和绝对性能承诺。
